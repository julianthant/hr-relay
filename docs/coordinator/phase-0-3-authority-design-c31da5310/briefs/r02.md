## Goal

Land the normative design for **one settings catalog and one protected `.tracker/settings/` root**
that owns every operator-managed non-provider-key local setting, as required by D327, so Phase 1.6
can implement it without redesign. Design only: **no file under `src/`, `tests/`, `scripts/`, or
`config/` changes** (D326). Fixture roadmaps under `tests/unit/architecture/fixtures/` are guard
fixtures and are out of scope.

## The four leaves you must close (roadmap node `phase0-settings-authority-design`, `builds:`)

1. Enumerate every setting once with schema, default, editability, sensitivity, restart scope, and
   owning consumer.
2. Place all operator-managed local configuration under one gitignored `.tracker/settings/` root;
   provider API keys alone remain in `.env`; runtime observations such as the host-derived display
   (D324) remain catalogued defaults rather than competing persisted settings.
3. Give Settings one revisioned update API and never return protected values after write.
4. Remove environment precedence for migrated non-provider-key leaves and forbid duplicate fallback
   authorities.

Doc `00` §0.3 Task 2 restates these as three checkboxes (enumeration; supersede D321's single-file
layout with the protected directory while retaining the state-root/database-journal coupling and
move username, password, timekeeper identity, local canary inputs, overrides, timeouts, paths, and
worker defaults there; provider-key-only `.env`, D324 default, write-only protected inputs with
presence/revision readback). Both must be ticked with evidence.
