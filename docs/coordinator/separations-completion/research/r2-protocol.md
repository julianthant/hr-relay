## One coherent protocol decision for the operator

Recommended proposal: prove deletion using a separately named, explicitly disposable pending transaction; keep the actual separation filing present through Kuali finalization. Each actual write requires its own later operator approval. The protocol must also choose an explicit target disposition: either a narrowly named exception permitting the legitimate actual filing and final Kuali result to remain (with their read-backs), or reversible test-instance targets whose restoration can be proved. The disposable target's intended final state and restoration/retention disposition must be explicit too. No general waiver of §3.2 is implied.

4589 is an operator-named historical candidate, not an automatically registered controlled target. Gone 4537 stays gone. No disposable transaction is inferred or created to obtain a witness. If a safe target/disposition cannot be named, criterion 5 remains blocked while UI inspection can proceed.

## Concrete implementation proposal after ratification

1. **Bind deletion to the approved live set, end to end.** Extend the sweep target/staging contract in `src/domain/ui/ucpath-smart-hr-termination.ts`, the pending read/probe/verify contracts, and `src/domain/contracts/ucpath/delete-pending-terminations.ts` with an exact canonical set of transaction identities and the facts approval binds. Build the permanent sweep key from person plus this approved set, not a run ID, retry token, arbitrary nonce or modified ledger. A newly observed empty set cannot permanently suppress a different later nonempty set. Retain the generic sequencer's permanent-key reuse and the existing filing key. Existing immutable intents remain immutable; define explicit old-shape compatibility/refusal rather than reinterpret their meaning.
2. **Make prepare obey that scope.** `src/stores/ucpath/driver/smart-hr-operation.ts:679` currently checks all matching rows. Change the read/stage/selection path and fake driver together so each selected row resolves to the approved transaction identity; fresh preparation must refuse changed, ambiguous, missing or newly appeared unapproved rows before a fence/click. For the existing all-pending-clear proof, require that the approved set is the complete eligible set; refuse extras rather than silently leave them or broaden deletion. The independent verify read must prove the declared outcome and preserve any protected real filing. Live read-only verification is required if the current page cannot expose stable row identity; no selector or identity may be guessed. A key-only fix is insufficient.
3. **Add real operator approval nodes to a supported controlled-proof composition before transaction acquisition.** D287's per-write approvals govern this proof ceremony; the ordinary separation graph deliberately has one identity gate. Preserve that ordinary gate UX. Reuse the existing step/harness composition mechanism to assemble the controlled-proof path with a typed write-approval packet for deletion, filing and finalization; do not silently add mandatory gates to every ordinary separation. Packets bind exact action, target/input digest and applicable prior receipt. Keep identity approval's separate meaning. Use the existing `src/core/run-executor.ts:1589–1605` gate park/resume mechanism; the gate must be outside prepare→commit (write-safety §14.3/D26). Extend strict gate payload, command validation, served ceremony and receipt plumbing where the new gate type requires it. Approval of one write must not release the next; stale or mismatched approvals refuse. The independent disposable proof must use a D265/D266-compliant supported step/harness composition with real admission, gates and receipts; the exact registered harness placement must be resolved within R3 against those folder/role rules, and any unavoidable change to the ordinary graph's gate contract returns to the coordinator as a product decision; no test-only registered rail, direct sequencer operational bypass, forged omission receipt or script that clicks live controls.
4. **Keep finalization attached to a surviving filing.** The real filing and its receipt stay in the filing→finalization chain; deletion proof is a separately approved target and cannot delete that chain's filing. Bind finalization to the exact durable successful filing receipt and verify its current UCPath presence/status through a typed read before offering finalization approval, then through the supported freshness boundary. Missing/deleted/denied/ambiguous filings refuse. Any refusal after filing preserves that durable receipt and never files again to repair finalization. D307's operator-asserted omission arm remains explicitly asserted and cannot be promoted into controlled-filing evidence.
