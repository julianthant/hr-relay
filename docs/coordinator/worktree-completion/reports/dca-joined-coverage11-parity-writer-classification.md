## Guard contract and classification

`tests/unit/architecture/parity-reference-authority.test.ts:255–280` implements a deliberately broad two-way structural arm:

- It scans every git-visible `.ts` file below `tests/parity` for either `writeFileSync` or `writeFile(` (lines 263–265).
- It accepts exactly `tests/parity/helpers/reference-store.ts`, the one `PARITY_UPDATE`-gated reference owner, and `tests/parity/helpers/bundle.ts`, whose writer is constrained to the built `dist/` stamp and separately forbidden from naming `references` (lines 259–262 and 276–279).
- It rejects both an unlisted writer and a stale listed writer (lines 266–274).

That shape implements the normative D132 rule in `docs/rebuild/reference/frontend-backend-integration.md` §7.1: an ordinary assertion run writes no reference file, and the semantic/pixel reference pair can refresh only under the one deliberate `PARITY_UPDATE=1` switch. `docs/rebuild/reference/guards-and-tests.md` §5 item 9 explicitly treats this out-of-Vitest parity lane as a ratchet arm that must remain able to fail.

The two writes are therefore **not production reference writes**: both destinations are generated by `test.info().outputPath`, both payloads are current-run `ariaSnapshot()` output, and both files immediately register the result as a Playwright attachment. They are nevertheless **guard violations** because a direct filesystem writer under `tests/parity` is indistinguishable to the structural arm from a future unconditional golden writer. The comments calling them ordinary output do not satisfy the enforcement contract and must not become an allowlist rationale.
