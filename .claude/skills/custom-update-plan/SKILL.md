# /custom-update-plan — one change, every plan view, one commit

## What this skill keeps in step

| View | Path | Role | Who edits it |
|---|---|---|---|
| **Plan SSOT** | `docs/rebuild/07-master-plan.md` (+ the owning doc for any new decision, + a one-line pointer in `docs/rebuild/04-reconciliation.md`) | normative — phases, order, exit criteria | this skill ONLY when the change is a ratified decision; otherwise untouched |
| **Roadmap source** | `docs/roadmap/roadmap.json` | the website's single source of truth: timeline nodes → tracks → chunks, each with `features` (what it builds, per layer + status) and `requires` (what it needs) | this skill, every time |
| **Roadmap site** | `docs/roadmap/index.html` | GENERATED by `npm run roadmap` — never hand-edited | regenerated every time |
| **Prose tracking view** | `ROADMAP.md` | DERIVED operator view (§1 at-a-glance, §2 completed, §3 active, §4 needed from you, §5 deferred) | this skill edits the matching lines every time |

**Doc 07 wins on any disagreement.** A decision is not ratified until it lands in its owning doc in the same commit that records it (project `CLAUDE.md`); this skill never mints a decision number on its own — re-read `docs/rebuild/04-reconciliation.md` at HEAD first (concurrent sessions collide on D-numbers).

## Step 0 — name the change

Restate the change in one line with its class, before touching anything:

- **status** — a node/track/chunk moved (`planned → active → done`, `you → done` when the operator acted, `proposed → planned` when ratified)
- **feature** — something got built / deferred / retired inside a node (add or re-status a `features` entry; tag its layer)
- **requirement** — a prerequisite was met, added, or removed (`requires`); a `you` item the operator answered flips `met: true`
- **node** — a new slice/track/order/deferral exists (new item with an `id`, its features and requires)
- **decision** — a D-number was ratified (owning doc + 04 pointer + the roadmap mentions it)
- **facts** — tiles/meta (`asOf`, `head`, counts: guards, tests, parity, schema version, decisions range, workflows migrated, the critical-path blocker)

If the user's request is vague ("update the roadmap"), derive the change list from `git log --oneline <last roadmap commit>..HEAD` and the diff of `ROADMAP.md` since then; state it; proceed.

## Step 1 — edit `docs/roadmap/roadmap.json`

The schema is in `scripts/generate-roadmap.ts` (zod, strict — an unknown key fails loud). Shape reminders:

- **Node** (`kind: "phase"`): `id`, `status`, `when {primary, secondary?}`, `phase` (eyebrow), `title`, `chip?`, `size?`, `summary`, `open`, `features?`, `requires?`, `items[]`, `notes?`. Also `kind: "flag"` (a dated milestone line) and `kind: "today"`.
- **Item** (nested under `items`, recursively): `id?`, `status`, `title`, `date?`, `chip?`, `size?`, `desc?`, `features?`, `requires?`, `table?`, `notes?`, `items?`.
- **Status**: `done | active | you | planned | proposed | never`. `you` = blocked on an operator act; `never` = won't build / deferred-with-trigger.
- **Feature**: `{ "text", "layer", "status"? }` — `layer` is one of `frontend` (React only) · `backend` (BFF/kernel only) · `both` (a vertical slice) · `wiring` (connecting two halves that already exist) · `docs` · `proof` (a live run / measurement). **Always tag the layer** — it is how the operator tells "not built yet" from "built and sloppy". `status` defaults to the node's; set it when a node is active/planned but this one feature is already `done` (or the reverse).
- **Requirement**: `{ "kind": "node", "ref": "<id>" }` · `{ "kind": "you", "text", "met" }` · `{ "kind": "fact", "text", "met" }`. A `node` requirement is met when the referenced node is `done`. `unlocks` is DERIVED (never written). Refs must resolve; cycles fail loud.
- **Ids** are stable anchors (`order-3`, `track-a`, `sep-6c`, `def-byte-path`) — never rename one; the dependency tree and deep links bind to them.
- Inline markup in any text: `` `code` ``, `**bold**`; D-numbers are auto-highlighted.

Also bump `meta.asOf` and `meta.head` (the commit this update describes — use the HEAD you are updating FROM; the skill's own commit comes after) and the `today` node text; refresh any tile the change moves.

## Step 2 — regenerate and check

```bash
npm run roadmap            # renders docs/roadmap/index.html; fails loud on schema, unknown ref, cycle
npm run roadmap -- --check # must print "fresh"
npx eslint scripts/generate-roadmap.ts --max-warnings 0   # only if the generator itself was touched
```

If the change needs a shape the schema does not have, extend `scripts/generate-roadmap.ts` (schema + renderer + CSS) in the same commit and run `npm run lint && npm run typecheck`.

## Step 3 — mirror into `ROADMAP.md`

Edit the lines the change touches, nothing else — §1's at-a-glance row(s), the matching bullet in §2/§3, the §4 "needed from you" block if a blocker appeared/cleared, §5 if a deferral changed. Keep its voice (dated, decision-numbered, one-line-per-fact). Never restructure it here.

## Step 4 — decisions (only when the class is `decision`)

The owning doc gets the normative text; `04-reconciliation.md` gets the one-line pointer; `roadmap.json` cites the D-number where it lands. If the owning doc was NOT updated in this or a prior commit, stop — the roadmap may not claim a decision the SSOT does not carry.

## Step 5 — verify, commit

- Open the site once headless and look at the node you changed (`playwright-cli -s=rm open http://127.0.0.1:<port>/index.html` over a throwaway `python3 -m http.server` in `docs/roadmap/`; `file:` is blocked) — a rendered check beats a green generator.
- Stage **only**: `docs/roadmap/roadmap.json`, `docs/roadmap/index.html`, `ROADMAP.md`, plus any owning docs from Step 4 and the generator if touched. Never `git add -A`.
- One commit: `docs(roadmap): <one-line change> — json + site + ROADMAP.md` (decision commits: `docs(<owner>): D<n> — …` first, then the roadmap commit, or both in one with the decision named).
- Never push.

## Step 6 — republish the artifact (when the operator uses the hosted copy)

The hosted page is the same `docs/roadmap/index.html`; republish via the Artifact tool **to the existing URL** (find it with `action: "list"` if this session does not have it) so the link stays stable. Keep title `HR Rebuild Roadmap` and favicon `🗺️`.

## Guardrails

- The JSON is the source; `index.html` is output. A hand-edit to the HTML is lost on the next run and `--check` will flag the drift.
- A feature marked `done` on the roadmap must be landed at HEAD — cite the commit/decision in its text. Do not pre-mark.
- `you` items are the operator's, not yours: flip `met` only on the operator's explicit answer, never on an assumption.
- The roadmap records **what is built and what is required**; it does not invent scope. A feature nobody planned is a finding for `docs/findings/`, not a roadmap row.
