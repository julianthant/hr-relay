# /custom-update-plan — one change, plan + site + owning docs, one commit

## What this skill keeps in step

| View | Path | Role | Who edits it |
|---|---|---|---|
| **Plan SSOT** | `docs/rebuild/07-master-plan.md` (+ the owning doc for any new decision, + a one-line pointer in `docs/rebuild/04-reconciliation.md`) | normative — phases, order, exit criteria | this skill ONLY when the change is a ratified decision; otherwise untouched |
| **The plan as written** | `docs/rebuild/14-roadmap.md` | the operator tracking view AND the roadmap site's single source — written in the notation below; the region between `<!-- roadmap:start -->` and `<!-- roadmap:end -->` is what renders; appendices after the end marker are prose | this skill, every time |
| **Roadmap site** | `docs/roadmap/index.html` | GENERATED by `npm run roadmap` — never hand-edited | regenerated every time |

**Doc 07 wins on any disagreement.** A decision is not ratified until it lands in its owning doc in the same commit that records it (project `CLAUDE.md`); this skill never mints a decision number on its own — re-read `docs/rebuild/04-reconciliation.md` at HEAD first (concurrent sessions collide on D-numbers).

## Step 0 — name the change

Restate the change in one line with its class, before touching anything:

- **status** — a node moved (`planned → active → done`; `you → done` when the operator acted; `proposed → planned` when ratified)
- **feature** — something got built / deferred / retired inside a node (a `builds:` line gains/changes its box and layer)
- **requirement** — a prerequisite was met, added, or removed (`needs:`); a `you:` item the operator answered becomes `you(met):`
- **node** — a new slice/track/order/deferral exists (a new heading with `{#id}`, its attributes, builds, needs)
- **decision** — a D-number was ratified (owning doc + 04 pointer + the plan cites it)
- **facts** — `asOf:` / `head:` / the `tiles:` strip (guards, tests, parity, schema version, decisions range, workflows migrated, the critical-path blocker) / the `## today:` line

If the request is vague ("update the roadmap"), derive the change list from `git log --oneline <last roadmap commit>..HEAD`; state it; proceed.

## Step 1 — edit `docs/rebuild/14-roadmap.md` in the notation

The parser is `parsePlan` in `scripts/generate-roadmap.ts`; every line inside the region must be one of these shapes or the build fails loud with the line number. The parsed plan is then validated by the same strict zod schema the page renders from.

### Notation

```
# HR Rebuild Roadmap                      ← title
asOf: 2026-08-20                          ← meta lines (asOf, head, eyebrow, footer; source: repeatable)
head: 5f6713f
> one-paragraph lede (one line)
tiles:
- Label | value | sub                     ← a tile; a leading "!" makes it the hot (amber) tile

<!-- roadmap:start -->

## Per-workflow migration — separations first {#phase-3}     ← a PHASE: "## Title {#id}" (id required)
phase: Phase 3                             ← eyebrow
status: active                             ← done | active | you | planned | proposed | never
when: 08-12 → today | nine days so far     ← primary | secondary (secondary optional)
size: XL                                   ← S | M | L | XL (optional)
chip: active                               ← optional; chip-tone: overrides the colour
open: yes                                  ← yes | no (unused by the tree; kept for the doc)

> summary — one line; more "> " lines are joined with a space

builds:                                    ← what this node BUILDS, one feature per line
- [x] BE text                              ← box = the feature's own status: [x] done · [ ] planned · [~] active · [?] proposed · [-] never · [!] needs you
- [ ] FE text                              ← LAYER = FE (React only) · BE (BFF/kernel only) · BOTH (vertical slice) · WIRE (connecting two halves that exist) · DOCS · PROOF (a live run / measurement)

needs:                                     ← what this node NEEDS
- sep-6c                                   ← another node's id (met when that node is done)
- you: name the §4f2 canary target(s)      ← an act only the operator can take (amber); you(met): once answered
- fact: capability register at zero open   ← a fact; fact(met): when true

note: text                                 ← a note block; note!: an amber (operator) note

### Track A · separations backend completion {#track-a}     ← a TASK under the phase: "### Title {#id}" (id optional; needed for needs:/links)
status: you
date: D196 · D205 live 08-13               ← the item's info line (dates, decisions)
size: L
chip: blocked at A1 — needs you

> desc
builds: … / needs: … / note: …
| # | Step | Status |                      ← a markdown table; first cell may start with ! (amber row) or ✓ (done row)
|---|---|---|
| !A1 | You name the canary | **YOU** |

#### 1 · new-kronos timecard read {#sep-1}   ← a SUB-TASK (#### and ##### nest one level each)

## flag: 2026-08-12 | D193 — scope and entry …   ← a dated milestone on the spine
## today: 2026-08-20 · HEAD 5f6713f · …          ← the TODAY rule

<!-- roadmap:end -->
```

Rules that keep the tree honest:
- **Every `builds:` line carries a layer tag** — it is how the operator tells "not built yet" from "built and sloppy".
- **A feature marked `[x]` must be landed at HEAD**; cite the commit/decision in its text. Never pre-mark.
- **`you:` items are the operator's** — switch to `you(met):` only on their explicit answer.
- **Ids are stable anchors** (`order-3`, `track-a`, `sep-6c`) — never rename one; links and deep links bind to them. `needs:` refs must resolve; cycles fail loud.
- Inline markup in any text: `` `code` ``, `**bold**`; D-numbers are auto-highlighted. No other markdown inside the region.
- The plan records **what is built and what is required**; it does not invent scope. An unplanned feature is a finding for `docs/findings/`, not a roadmap line.

Also bump `asOf:` and `head:` (the HEAD you are updating FROM), the `## today:` line, and any tile the change moves.

## Step 2 — regenerate and check

```bash
npm run roadmap            # renders docs/roadmap/index.html; fails loud on a bad line, unknown ref, cycle, or schema miss
npm run roadmap -- --check # must print "fresh"
npm run roadmap -- --json  # the parsed plan, if you need to inspect the structure
npx eslint scripts/generate-roadmap.ts --max-warnings 0 && npm run typecheck   # only if the generator was touched
```

If the change needs a shape the notation does not have, extend `parsePlan` + the schema + the renderer in the same commit.

## Step 3 — decisions (only when the class is `decision`)

The owning doc gets the normative text; `04-reconciliation.md` gets the one-line pointer; the plan cites the D-number where it lands. If the owning doc was NOT updated in this or a prior commit, stop — the roadmap may not claim a decision the SSOT does not carry.

## Step 4 — verify, commit

- Look at the node you changed once, rendered: `cd docs/roadmap && python3 -m http.server 8765 --bind 127.0.0.1 &` then `playwright-cli -s=rm open http://127.0.0.1:8765/index.html` (the `file:` scheme is blocked). A rendered check beats a green generator. Stop the server after.
- Stage **only**: `docs/rebuild/14-roadmap.md`, `docs/roadmap/index.html`, plus any owning docs from Step 3 and the generator if touched. Never `git add -A`.
- One commit: `docs(roadmap): <one-line change> — plan + site` (decision commits: `docs(<owner>): D<n> — …` first, or both in one with the decision named).
- Never push.

## Step 5 — republish the hosted copy

Republish `docs/roadmap/index.html` via the Artifact tool **to the existing URL** — `https://claude.ai/code/artifact/8e678086-ab5f-44c0-8fdb-f04986fb95ff` (pass it as `url`; `action: "list"` also finds it) — so the link stays stable. Keep title `HR Rebuild Roadmap` and favicon `🗺️`.

## Guardrails

- `docs/rebuild/14-roadmap.md` is the source; `index.html` is output. A hand-edit to the HTML is lost on the next run and `--check` flags the drift.
- Prose that is not a node belongs **after** `<!-- roadmap:end -->` (the appendices) or in the owning docs — never inside the region.
- Other sessions edit `docs/rebuild/14-roadmap.md` too: take `git status` first; stage your hunks only; a concurrent edit inside the region that breaks the notation is theirs to fix, not yours to revert — `npm run roadmap` names the line.
